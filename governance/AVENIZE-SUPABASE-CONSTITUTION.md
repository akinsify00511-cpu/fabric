# AVENIZE SUPABASE CONSTITUTION

## 1. Objective
Supabase is a governed execution layer. The live database must be deterministically derivable from version-controlled migrations and machine-readable manifests.

## 2. Canonical naming
- Tables: plural `snake_case` nouns.
- Columns: `snake_case`.
- Primary keys: `id` using the project-standard UUID strategy.
- Foreign keys: `<referenced_entity>_id`.
- Functions/RPCs: `<verb>_<object>`; stable public contracts are explicit.
- Triggers: `trg_<table>_<event>`.
- Indexes: `idx_<table>_<columns>`.
- Constraints: `ck_<table>_<rule>`, `uq_<table>_<columns>`, `fk_<table>_<column>`.
- Views: `vw_<purpose>`; materialized views: `mv_<purpose>`.
- Edge Functions: kebab-case.
- Migration names: generated by the Supabase CLI and descriptive; never hand-invent timestamps.

## 3. Migration law
- Applied production migrations are immutable.
- New changes require a new migration.
- Migrations must be dependency-safe and fail atomically where practical.
- Destructive migrations require explicit approval and backup verification.
- Migrations must be idempotent where the operation semantics allow it.
- No `fix-final`, `latest`, `new`, or ad-hoc migration naming.

## 4. Database object registry
Every production object must be represented in a manifest with: name, type, owner, purpose, source migration, dependencies, exposure, security classification and verification test.

## 5. RPC contract law
Every RPC used by application code must have:
- canonical name;
- input schema;
- output schema;
- authorization rule;
- error contract;
- owning domain;
- migration source;
- production verification test.

An application call to an unregistered RPC is a build/release failure.

## 6. RLS and exposure
Every table in an exposed schema must have RLS enabled and policies matching the actual authorization model. Authentication alone is never authorization. Authorization must be based on trusted server-side ownership/role data, not user-editable metadata.

Views exposed to application roles must use an explicitly reviewed security model. Privileged functions must be minimized, scoped and audited.

## 7. Schema drift
The constitution validator must compare:
`manifest ↔ migrations ↔ local schema ↔ production schema ↔ application contracts`.

Missing, unexpected or incompatible objects are drift. Critical drift blocks release.

## 8. Reconciliation
Safe reconciliation follows:
`backup → inspect → dependency plan → apply canonical migration → verify → contract test → record result`.

The reconciler must never invent schema from an error message when a canonical source is unavailable.

## 9. Production gate
Production is GREEN only when required tables, columns, RPCs, policies, triggers, views, functions and extensions pass the registered contract tests.
