# Avenize Contract Constitution — Client-Payment Readiness

**Status:** Constitution · **Scope:** the entire stack · **Authoritative boundary:** repository

This constitution is the doctrine behind Contract Integrity as a **P0 readiness gate**,
not a technical clean-up exercise. It defines the canonical contracts the production
System holds itself to, the single-money-vocabulary rule, and the definition of *done* for
client-payment readiness.

Its enforcement mechanism is the **Contract Sentinel** (`scripts/verify_production_contract.py`
+ `scripts/verify-production.sh` + `scripts/e2e-production.sh` + the DB-side
`run_integrity_scan()`), which is *permanent and wired into CI/deploy* — it is not a
one-off audit.

---

## Article I — The single rule

A feature is **not complete** because the UI renders. It is complete only when

```
UI → application logic → RPC/API → database → permissions → external service → resulting state
```

all **agree**.

Every contract below exists to make that chain checkable automatically. When a page,
RPC, table, permission, or external-service call disagrees with its canonical definition,
that is a **contract violation** — a P0 defect that goes in the readiness gate, not a
one-off manual patch.

---

## Article II — The canonical contract layers

### II.1 Database / RPC contracts (P0)

Every production RPC has **one canonical definition**: name, argument names, argument
types, return type, permissions, tables touched, expected frontend caller, and expected
business/user context. The canonical source is the **migration chain**
(`supabase/migrations/*.sql`, applied in filename order, later files win). The
machine-readable statement of it is `supabase/contract/production_contract.json`,
generated by `scripts/generate_contract_manifest.py`.

Checks the Sentinel enforces continuously:

- RPC names canonicalized (no divergent spellings of the same procedure).
- RPC argument names + types canonicalized (type aliases unified: `int→int4`,
  `decimal→numeric`, `bigserial→int8`, `character varying→text`, `timestamptz`, … —
  kept in sync across the generator, the SQL normalizer, and the live comparator).
- RPC return structures canonicalized.
- Overloaded RPCs eliminated where unnecessary; old versions dropped, remaining
  deprecated ones marked and not called by the frontend.
- Frontend callers mapped to the canonical RPC (the generator FAILS on any
  frontend RPC reference with no canonical definition).
- RLS + service-role-only + business/ownership rules documented per object.
- Security-sensitive objects (`SECURITY_REPAIR_REQUIRED`) are never auto-repaired.

**Canonical auth/identity RPCs** (the letters the journeys depend on):

| Function | Contract |
|---|---|
| `create_business_and_owner(p_business_name, p_industry, p_staff_name, p_job_title)` | One idempotent onboarding transaction: auth identity → organization → business → organization membership → owner staff. Guarded: `auth.uid()` null → `42501`; `pg_advisory_xact_lock` prevents duplicate businesses; existing staff → "User already belongs to a business". Sets `organization_id`. |
| `resolve_current_user_context()` | Canonical `auth.uid() → staff → business` resolver used by onboarding and app routing. |
| `ensure_business_organization()` | Data-contract trigger: guarantees every business has an organization before the `organization_id NOT NULL` constraint is enforced. |
| `refresh_business_metrics()` | Authenticated adapter — resolves the caller's business before refreshing governed metrics (the zero-arg overload). |

### II.2 Data / ownership contracts (P0)

One authoritative ownership chain, resolved server-side — never independently
reconstructed differently on different pages:

```
auth.users
   ↓  auth.uid()
staff
   ↓  staff.business_id
business
   ↓  business.organization_id
organization
   ↓
business data (RLS: business_id IN (SELECT business_id FROM get_current_staff()))
```

Rules:
- **One user → one business** through the onboarding path (`create_business_and_owner`
  is idempotent + advisory-locked → duplicate business/owner prevention).
- **`organization_id` is never null** — enforced by the `ensure_business_organization`
  trigger and the canonical contract.
- **Existing-business/onboarding detection** uses `staff.business_id` (owned by the
  server), never a client-side flag. A returning user is *recognized*, not re-onboarded.
- FKs, orphan detection, and cross-business access are checked by the Sentinel +
  RLS (tenant isolation: member sees own rows; outsider sees none).

### II.3 Auth / onboarding contract (P0)

```
Authentication → session → identify user → existing membership → existing business →
onboarding state → route accordingly
```

**Never** `new login → assume new user → create business → crash because it exists`.
`create_business_and_owner` raises `'User already belongs to a business'`; the client
reconciles by refreshing membership and routing to `/app`. Refresh never restarts
onboarding; logout/login never corrupts state.

### II.4 Payment contract (P0 — the money contract)

Pipeline, canonical and single-sourced:

```
Pricing → subscription-management → payment_transactions → Paystack →
paystack-webhook → Paystack verification → business_subscriptions → business_entitlements
```

The **browser never decides "Payment succeeded."** Only the server (webhook →
re-verification → ledger settlement) does.

**The one pricing constitution.** There is exactly one canonical plan vocabulary and it is
**not configurable per page**:

```
starter  team  business  pro  scale
```

(`enterprise` remains an accepted alias for bespoke arrangements; `professional` /
`growth` are NOT used — when they appear they are aliases recorded in
`business_entitlements.plan` CHECK, never competing product names.)

Billing cycles are canonical: `monthly` / `yearly` (kobo/NGN; `_cents` columns).
Prices come from `pricing_tiers` (server-side lookup via `plan_price_cents`) — the
browser never supplies a price. Founding-period / future-price changes are a
`pricing_tiers` config change, not a code change.

Checked: canonical plan codes · billing cycles · server-side price lookup · checkout
initiation · payment ledger creation · idempotency · webhook signature verification ·
Paystack re-verification · amount verification · payment state machine
(`pending→processing→success|failed`, `success→refunded`) · subscription activation ·
entitlement activation · cancellation (access until period end) · renewal · failed
payment · refund · payment history · receipt email · payment investigation.

### II.5 Notification / email contract (P0/P1)

```
event → email event → notification processor → queue_email → email-service → Resend →
delivery status
```

Canonical: `email_events` (internal delivery ledger), `transactional_email_templates`
(19 seeded), `queue_email` RPC (membership-guarded), `fanout_email_event` +
`queue_payment_lifecycle_email` + `queue_subscription_lifecycle_email` triggers,
`email-service` (renders + delivers via Resend, writes `provider_message_id` back),
`resend-webhook` (signature-verified, advances ledger **forward only**).

Email is **event-driven** (queued by triggers, never inline in a request path). A
receipt-email failure can never break payment settlement.
`send-email-notification` is a legacy edge function; the canonical outbound path is
`email-service`. The Sentinel checks `queue_email` exists + `email-service` /
`resend-webhook` are deployed.

### II.6 Frontend / API contract (P0)

Every frontend data call is contracted. The generator scans `src/**` for
`.from/.rpc/.storage.from/.functions.invoke` and fails on any reference without a
canonical definition. The Sentinel compares expected params/return shapes against live
PostgREST (spec-mode signature drift; probe-mode existence). This is how the old
`refresh_business_metrics` 400-class mismatch class is caught **automatically** from the
repository, not discovered from a browser console.

## Article III — Client-payment readiness: the definition of *done*

We stop asking "how many features did we ship?" and ask:

> **Can a real customer safely sign up, use Avenize, pay us, receive what they paid for,
> and return tomorrow without their data or account breaking?**

Readiness is a **gate result**, produced by the Sentinel and the journey tests. The
three critical journeys that decide it are P0; everything else may be iterative.

**Journey A — New customer:** landing → pricing → signup → OAuth/email → onboarding →
business created → dashboard.
**Journey B — Returning customer:** login → existing account → existing business →
existing onboarding → dashboard. MUST NOT recreate business, MUST NOT restart onboarding.
**Journey C — Paying customer:** pricing → checkout → Paystack → webhook → verification →
subscription → entitlement → dashboard access → receipt, with a real transaction.
**Journey D — Failed payment:** checkout → failed payment → **no entitlement** → clear
user message → retry.
**Journey E — Cancellation:** cancel → access remains until period end → expires →
entitlement downgraded.

Only when every P0 journey passes does the gate report:

```
CLIENT PAYMENT GATE   PASS
```

and only then do we declare: **🟢 Avenize is ready for paying clients.**

## Article IV — Enforcement (the Contract Sentinel)

The Sentinel is code, committed, and wired into CI + deploy — it is the permanent
mechanism that prevents falling back into the fix-one-error-per-month cycle.

- **`scripts/generate_contract_manifest.py`** — canonical contract extraction + coverage
  (runs in CI `contract-manifest`; the generated artifacts must be committed).
- **`scripts/verify_production_contract.py`** — compares the canonical contract against
  live PostgREST/Storage/Edge functions; classifies OK / CONTRACT_DRIFT / MISSING /
  SECURITY_REPAIR_REQUIRED; prints `CONTRACT HOLDS` or `CONTRACT BROKEN`.
- **`scripts/verify-production.sh`** — the deploy gate (Auth health, contract, Payments
  + Email edge functions, SPA shell). `PRODUCTION READY` or fail.
- **`scripts/e2e-production.sh`** — the journey gate (signup → onboarding → membership →
  intelligence → payment rails → email rail). `E2E READY` or fail.
- **`run_integrity_scan()`** — DB-side scanner over `integrity_rules` (the same
  contract, seeded server-side) for on-Platform health checks.

An honest failure in any of these is **the gate working**, not an incident to paper over.

## Article V — Lanes / ordering

- **🔴 Lane 1 (before money):** auth · onboarding/data identity · DB contracts ·
  critical RPCs · payment · subscriptions · entitlements · email receipts · RLS/security ·
  production E2E. *Everything in this constitution that is P0 lives here.*
- **🟡 Lane 2 (good enough for clients):** dashboard · core workflows · CRM · meetings ·
  capture · analytics · notifications · error states · UX consistency.
- **🟢 Lane 3 (after launch):** polish · secondary modules · advanced intelligence ·
  non-critical automations · mobile · integrations · nice-to-have.

Immediate sequence: **1. Canonical Contract Constitution → 2. Contract Sentinel →
3. Production DB/RPC reconciliation → 4. Auth/onboarding certification →
5. Payment certification → 6. Critical E2E → 7. Client-payment GO →
8. Marketing + mobile in parallel.**
